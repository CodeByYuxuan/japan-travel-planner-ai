# Production Deployment

Ticket T-036 selects the following managed deployment targets:

| Component | Target               | Repository configuration |
| --------- | -------------------- | ------------------------ |
| Web       | Vercel               | `vercel.json`            |
| API       | Render Web Service   | `render.yaml`            |
| Database  | Render PostgreSQL 16 | `render.yaml`            |

The Vercel project and Render Blueprint must both use the repository root. The
configuration assumes the production branch is `main`.

## Temporary Free Demo

The checked-in Blueprint selects `free` instances for the Render API and
PostgreSQL database in the Singapore region. Use a personal Vercel project on
the Hobby plan for the web app. This setup is for a temporary demonstration,
not durable production.

Render free instances have important operational limits:

- The API spins down after 15 minutes without inbound traffic and can take about
  one minute to wake.
- A workspace receives 750 free web-service instance hours per month.
- Only one free Render PostgreSQL database can be active per workspace.
- The free database is limited to 1 GB and expires 30 days after creation.
- An expired database has a 14-day upgrade grace period before deletion.
- The free database has no backups or managed connection pooling.

Do not store durable or irreplaceable data in this environment. Export any demo
data that must be retained before the database expires. See the official
[Render free-instance limits](https://render.com/docs/free),
[Render Blueprint reference](https://render.com/docs/blueprint-spec), and
[Vercel Hobby plan](https://vercel.com/docs/plans/hobby) before provisioning.

## Required Configuration

No secret values belong in the repository.

### Vercel

Set these Production environment variables in the Vercel project:

| Variable              | Required | Purpose                                                      |
| --------------------- | -------- | ------------------------------------------------------------ |
| `VITE_API_BASE_URL`   | Yes      | Public HTTPS URL of the Render API, without a trailing slash |
| `VITE_TRIP_DATA_MODE` | Yes      | Set to `api` for the persisted production flow               |

Both values are embedded in the client bundle and are not secrets.

### Render

The Blueprint provisions or prompts for these values:

| Variable         | Source                              | Purpose                                        |
| ---------------- | ----------------------------------- | ---------------------------------------------- |
| `DATABASE_URL`   | Render PostgreSQL connection string | Prisma runtime and migrations                  |
| `WEB_ORIGIN`     | Enter during Blueprint creation     | Exact Vercel production origin allowed by CORS |
| `JWT_SECRET`     | Generated by Render                 | Anonymous session cookie signing               |
| `OPENAI_API_KEY` | Enter during Blueprint creation     | AI itinerary generation                        |
| `OPENAI_MODEL`   | Repository configuration            | Model name already used by the API             |
| `PORT`           | Injected by Render                  | Public API listener port                       |

Optional provider features can be enabled later in the Render dashboard with
`GOOGLE_MAPS_API_KEY`, `WEATHER_API_KEY`, `RAKUTEN_APP_ID`, and
`RAKUTEN_ACCESS_KEY`. Their values must remain in Render, never in Git.

When `NODE_ENV=production`, the API marks its anonymous session cookie
`SameSite=None; Secure` so credentialed requests can cross the Vercel and Render
origins. Browser privacy settings can still block third-party cookies. For a
durable public launch, prefer custom web and API subdomains under the same
registrable domain and repeat the save/reopen smoke check.

## First Deployment

1. Import the GitHub repository into Vercel.
2. Keep the Vercel project Root Directory at the repository root and set the
   Production Branch to `main`.
3. Let Vercel create the project once to obtain its production origin. The first
   build can use a temporary `VITE_API_BASE_URL`; it is replaced after the API
   exists.
4. In Render, create a Blueprint from the same repository and `render.yaml`.
5. Enter the exact Vercel origin for `WEB_ORIGIN` and provide
   `OPENAI_API_KEY`.
6. Wait for Render to provision PostgreSQL, build the API, run
   `prisma migrate deploy` from the API start command, and pass `/api/health`.
7. Copy the Render API HTTPS URL into Vercel as `VITE_API_BASE_URL`, set
   `VITE_TRIP_DATA_MODE=api`, and redeploy the Vercel production deployment.

The production database is not seeded automatically. Production deploys apply
committed migrations only.

## Deployment From Main

- Vercel's Git integration deploys its Production Branch after a commit reaches
  `main`.
- Render tracks `main` and uses `autoDeployTrigger: checksPass`, so the API
  deploy starts only after GitHub checks pass.
- Render free web services do not support pre-deploy commands. The API start
  command runs idempotent committed migrations before starting the server.
  This also runs after a cold start and can add to wake-up time.

Provider Git integrations are the deployment mechanism for T-036. A duplicate
GitHub Actions deployment workflow is intentionally not configured, which
avoids storing provider deployment tokens in GitHub and avoids double deploys.

## Pre-Deployment Validation

Run from the repository root:

```bash
nvm use
corepack enable
corepack prepare pnpm@10.14.0 --activate
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm --filter @japan-travel-planner/api db:validate
pnpm test:e2e
git diff --check
```

If the Render CLI is installed, authenticated, and has an active workspace,
validate the Blueprint without creating resources:

```bash
render blueprints validate render.yaml
```

The Vercel configuration can be checked locally by parsing `vercel.json` and
running its declared web build command. A full `vercel build` requires the
project to be linked and its Production environment variables to be available.

## Post-Deployment Smoke Check

The automated smoke test exercises the built web app against the real API and
database while intercepting only AI generation and optional provider requests.
This keeps the run deterministic and avoids third-party usage charges. Trip
persistence, reopening, public sharing, and cleanup still use the deployed API.

To run the same production-like flow locally, start PostgreSQL on port 5432 and
run:

```bash
pnpm test:e2e:production
```

The local runner applies committed migrations, starts the API on port 3101,
builds and previews the web app on port 4173, runs the smoke test, and deletes
the trip it created. Override the database only when needed:

```bash
PRODUCTION_SMOKE_DATABASE_URL=postgresql://user:password@localhost:5432/database \
  pnpm test:e2e:production
```

To test a deployed environment, use the GitHub Actions `Production smoke`
workflow and provide the deployed web origin, or run:

```bash
PRODUCTION_SMOKE_BASE_URL=https://your-web.example.com \
  pnpm test:e2e:production
```

The deployed web app must be configured for API mode and point at the deployed
API. The smoke test intentionally writes one trip to the environment database
and deletes it after validating the read-only share page.

1. Request `https://<render-api>/api/health` and confirm HTTP 200 with
   `"status":"ok"`.
2. Open the Vercel root page and confirm API mode is active.
3. Open a `/share/<token>` URL directly in a new tab to verify the SPA rewrite.
4. Generate, edit, save, refresh, and reopen an itinerary.
5. Create a public share link and verify its read-only view.
6. Export both private and public itinerary PDFs.
7. Confirm the browser has no CORS failures and no requests to
   `localhost:3001`.

## Manual Deploy And Rollback

Vercel and Render both allow a manual redeploy from their dashboards. Use the
provider dashboard to redeploy a known commit or restore a previous application
deployment. Database migrations are forward-only. The free database has no
managed backups, so export important demo data before a destructive migration
and prepare a corrective migration instead of rolling the schema backward.
